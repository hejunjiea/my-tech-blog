DevOps 最初的想象是“开发自己运维”，几年实践下来，真正的落点变成了“把运维能力做成产品”。这篇笔记记录我观察到的五个方向，它们共同回答一个问题：如何让交付更稳定，而不是让流程更复杂。

## 一、平台工程取代散落的脚本

过去每个团队各自维护一套脚本，久了就没人敢动。平台工程的做法是把构建、部署、回滚、环境申请做成自助服务，把最佳实践固化进模板。开发者拿到的是“一条命令”，而不是“一份文档加十个坑”。

- 以开发者为中心设计入口，而非以工具为中心
- 默认配置即安全、即合规
- 异常路径与正常路径同样重要

## 二、GitOps 让状态可追溯

把集群的期望状态写进仓库，由控制器持续对齐。带来的直接好处是：任何变更都有提交记录，回滚就是一次 revert，而不是深夜凭记忆操作。

```
# 期望状态即代码
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
```

> 当“发生了什么”可以被 diff 出来，事故复盘才真正开始有意义。

## 三、基础设施即代码趋于成熟

IaC 早已不是新概念，但近期的变化在于：状态管理更可靠、策略检查更前置、多环境复用更顺畅。关键是把“检查”放在合并之前，而不是等到 apply 时才报错。

实践建议：先在 CI 里跑 plan 并展示差异，再让人决定是否合并，最后才执行变更。

## 四、供应链安全成为必选项

依赖来源、构建产物、镜像签名，正在从“加分项”变成“准入条件”。生成软件物料清单、校验构建可复现性、对发布产物签名，这些动作越早接入成本越低。

- 记录依赖与构建环境，保证可追溯
- 构建与发布产物做完整性校验
- 把安全检查嵌入流水线，而不是事后扫描

## 五、AI 进入运维的日常

告警聚合、日志归因、变更风险提示，是当前落地最成熟的三类场景。它们不会替代人做决策，但能显著缩短“从报警到定位”的时间。前提是数据要干净：指标、日志、追踪的标识必须统一。

## 小结

DevOps 的演进方向并不是引入更多工具，而是把确定性做进流程：状态可追溯、变更可预演、失败可回退。工具会继续更替，但这三条判断标准大概不会变。

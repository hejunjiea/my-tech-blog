上一篇聊了 Substrate 的基本用法，但「Hook」这个词背后其实有几种完全不同的实现层次。选错层次，轻则无效，重则崩溃且难以定位。这篇把三种主流机制拆开讲清楚。

## 一、Objective-C 方法交换

最常用的一层，依赖运行时的方法列表。核心是替换某个 selector 对应的函数指针，同时保留原实现以便调用。

```
%hook LoginManager
- (BOOL)isVip {
    return YES;
}
%end
```

**适用**：有明确类名与方法名的 Objective-C 方法。
**注意**：参数类型与返回值必须完全一致；结构体参数尤其容易因调用约定不符而崩溃。

## 二、C 函数符号重绑定

Swift 方法、C 函数、系统调用不走消息转发，方法交换对它们无效。这时需要改符号绑定——典型方案是 fishhook：遍历 Mach-O 的懒加载符号表，把目标符号指向自己的实现。

```
// 伪代码：把 open 重定向到 my_open
rebind_symbols((struct rebinding[1]){{"open", my_open, (void *)&orig_open}}, 1);
```

**适用**：`open`、`stat`、`objc_msgSend` 这类导入符号。
**局限**：只能拦截「通过符号表导入」的调用；如果目标在同一镜像内直接调用内部函数，或者编译时已内联，就拦不到。

## 三、指令级 inline hook

直接改目标函数开头的机器指令，跳转到自己的实现，执行完再跳回。它不依赖符号，也不需要方法名，因此对 Swift 静态派发、C++ 虚函数、被裁剪符号的函数都有效。

代价是复杂度高：

- 需要处理指令长度对齐，确保改写后不破坏原指令
- 要区分 ARM64 与 ARM64e（后者有指针认证）
- 并发调用与线程安全要自己保证
- 系统更新后偏移与指令形态可能变化

## 四、怎么选

一个实用的判断顺序：

1. 目标能被 `%hook` 拦到吗？能就优先用方法交换，成本最低
2. 是导入的 C 符号吗？用符号重绑定
3. 以上都不行，才考虑 inline hook

> 越往下越强大，也越脆弱。能用上层解决的，不要为了「更彻底」而下沉到指令层。

## 五、常见坑

- **Hook 生效但没被调用**：确认目标方法真的在调用链上，先打日志验证，再动手替换
- **偶发崩溃**：多见于 inline hook 的指令改写不完整，或线程竞争下指令处于中间状态
- **越狱环境正常、非越狱失效**：检查注入方式与签名，而不是怀疑 Hook 逻辑
- **升级系统后行为变化**：符号偏移与指令形态都会变，硬编码偏移的方案必须重新校准

## 小结

方法交换解决「对象行为」，符号重绑定解决「函数入口」，inline hook 解决「任意指令位置」。理解它们的分层，比记住某个 API 更有价值——因为选对层次，问题往往在写第一行代码之前就已经解决了一半。

前端的技术迭代向来密集，但真正能留下来、改变日常写法的东西并不多。这篇笔记不追热点，只挑出我最近半年在真实项目里感受到明显变化的五件事，按影响程度排序。

## 一、构建工具正在被重写

以 Rust 和 Go 实现的新一代打包器，把冷启动和增量构建的时间压缩到了几秒级。项目一旦变大，这种差异会非常直观：改一行代码，等待从十几秒变成几百毫秒，反馈循环的质量完全不一样。

```
// 典型的新一代工具链配置
export default defineConfig({
  build: { target: "es2022" },
  server: { hmr: true }
});
```

迁移成本主要在插件生态，而不是语法。建议新项目直接用新工具，老项目按模块逐步替换。

## 二、服务端组件重新划分了边界

“把组件放到服务端渲染、只把交互部分发给浏览器”正在成为主流思路。它带来的不只是首屏更快，更重要的是改变了数据获取的位置：组件可以直接读数据，不必再为每个页面写一层接口。

- 静态内容在服务端生成，减少客户端 JS
- 交互区域明确标注，职责边界更清晰
- 数据获取与视图就近放置，减少跨层传递

> 渲染位置的选择，本质上是一次对“什么该在用户设备上发生”的重新思考。

## 三、类型安全正在贯穿全链路

从数据库结构到接口契约再到前端组件，端到端类型推导已经可以做到几乎不用手写类型。改字段时编译期就报错，比上线后才发现的运行时错误便宜太多。

实践上建议先统一数据模型的定义来源，再让各层从同一处推导，而不是各写一套类型再手动对齐。

## 四、AI 辅助 coding 成为日常

代码补全已经从“猜下一个词”进化到“理解上下文后生成整段实现”。但真正提效的前提是给足上下文：清晰的目录结构、一致的命名、可读的组件边界，都会直接影响建议质量。

> AI 不会让糟糕的结构变好，反而会把混乱放大得更快。

## 五、运行时性能重新被重视

在框架能力趋同之后，差异开始回到细节：包体积、首屏交互延迟、长列表渲染。测量工具比以往更完善，建议每个新页面都先跑一遍真实设备的性能面板，再决定是否引入某个库。

## 小结

这些变化的共同点是：把复杂度从“运行时”移到“构建时与结构设计上”。工具会继续换，但判断标准不变——更快的反馈、更清晰的边界、更可预测的运行时表现。

云原生这几年最大的变化，是“堆组件”的阶段基本结束了。大家开始关心另一类问题：能不能更少侵入、更少资源浪费、更少运维负担。这篇笔记记录五个我认为已经跨过实验期的方向。

## 一、eBPF 成为观测与网络的底座

不修改应用、不注入动态库，就能在内核层面拿到网络与系统调用信息。它让“无侵入观测”变得可行：调用链、连接关系、延迟分布，都可以从内核直接采集。

- 适合：网络追踪、性能归因、安全策略
- 代价：需要理解内核语义，调试门槛偏高
- 关键：探针开销要经过压测验证再上线

## 二、服务网格走向轻量化

早期的 sidecar 方案把每个 Pod 都塞进一个代理，资源与延迟成本都不低。现在的方向是减少数据面跳数、把代理能力下沉到节点或内核层，让服务治理重新变成“透明的”。

> 好的基础设施应该被忘记。当你意识到它存在时，通常是因为它拖慢了请求。

## 三、事件驱动与按需伸缩

基于事件的自动伸缩让服务在无流量时真正降到零。它特别适合异步任务、消息消费与批处理。落地难点不在伸缩器，而在冷启动与背压：突发流量下必须有排队与限流策略。

```
# 期望副本数由队列长度决定
triggers:
  - type: queue
    metadata:
      targetLength: "10"
```

## 四、多集群与统一控制面

单集群不再是唯一形态。地域容灾、资源隔离、混合云需求推动着“多集群统一编排”：用一份声明描述应用，由控制面决定它落在哪、如何分发流量。复杂点在于网络打通与状态一致性。

- 先统一配置与发布流程，再统一运行时
- 流量调度策略要显式声明，避免隐式行为
- 跨集群的数据一致性单独设计，不要默认透明

## 五、WebAssembly 作为运行单元

Wasm 的启动速度与隔离性，使它在边缘函数、插件系统和多语言扩展场景里越来越常见。它当前的短板是生态与调试体验，但如果你的场景需要“安全地运行第三方代码”，它是很值得评估的选项。

## 小结

这五个方向的共同目标很清楚：让基础设施更透明、更按需、更少副作用。判断一项云原生技术是否值得引入，我通常只问三个问题——它减少了哪种运维动作？它的失败模式是否可控？出问题时我能在几分钟内定位？
